# Stage 1 implementation audit

> **Stage 2B Milestone 4 update — 2026-09-21:** the protected staff UI is implemented. Active approvers with current responsibilities receive `/dashboard`, `/review`, and assignment-scoped `/review/[id]`; active administrators additionally receive `/admin/unassigned` and the unassigned count. The pages use PostgreSQL-backed services shared with the existing GET APIs and the existing transactional decision POST. Search, status/resource/date filters, bounded pagination, empty/loading/service-error states, sanitized detail fields, immutable history, approve/deny/return confirmation, reason validation, pending submission prevention, idempotent retries, stale refresh, and the approval-versus-activation boundary are represented. Role-specific navigation hides requester actions but is never used as the authorization boundary. Users, resources, reports, permissions/activation, final audit UI, external notification delivery, delegation, reassignment, and analytics remain clearly deferred. No migration was added.
>
> Automated browser acceptance now resets and seeds only a `TEST_DATABASE_URL` whose parsed database name ends in `_test`; the Next test server opts into that URL through `PERMORA_E2E_DATABASE=isolated-test`. It covers live staff sessions, scope isolation, enumeration resistance, decisions, idempotency-key reuse, duplicate-click prevention, stale results, administrator-only unassigned records, focus/Escape behavior, and 390/320px overflow. These fixtures are test records and never fall back to the development URL.

> **Stage 2B Milestone 3 update — 2026-09-20:** the protected decision API is implemented at `POST /api/review/requests/:id/decision`. Approve, deny, and return-for-revision require a server-trusted active approver, the persisted assignment, full current responsibility coverage, a matching origin, validated JSON, optimistic version, and UUID idempotency key. Approval rechecks current requester eligibility, policy, resource/permission availability, scope assignments, validity, entitlements, and approved-request conflicts. Migration `0006` adds durable idempotency and recipient-scoped notifications. Each successful operation commits its decision, request state/version, assignment completion, immutable request/audit events, and notification in one transaction; approval creates no active access. The final `/review` UI, requester notification UI, activation, and provisioning remain unavailable.

> **Stage 2B Milestone 2 update — 2026-09-20:** the protected approval read API is implemented at `GET /api/review/requests`, `GET /api/review/requests/:id`, and `GET /api/admin/unassigned-requests`. Identity, active status, roles, responsibilities, and assignments come only from the Better Auth session and PostgreSQL. Normal review reads require the persisted assignee and current full-scope responsibility; unauthorized and nonexistent detail IDs share the same not-found response. The separate unassigned-routing query requires an active administrator. Responses use explicit sanitized DTOs, validated filters, bounded deterministic pagination, and private/no-store caching. The `/review` and administrator pages remain deferred UI placeholders; no decision endpoint, activation, or provisioning was added.

> **Stage 2B Milestone 1 update — 2026-09-20:** the PostgreSQL approval foundation is implemented in migrations `0004` and `0005`. Each newly submitted request is either assigned transactionally to one fully eligible approver and moved to `pending_review`, or preserved unassigned as `pending_routing`. Server-only domain code enforces full-scope responsibility matching, self-approval exclusion, open-assignment load balancing, assigned-approver-only decisions, optimistic concurrency, terminal approve/deny/return transitions, and atomic immutable decision/audit events. A guarded, dry-run-by-default reconciliation CLI handles older pending records. Administrator routes and controls remain deferred placeholders; activation and downstream provisioning remain unimplemented.

> **Stage 2A update — 2026-09-20:** the requester runtime has been cut over from the browser prototype described in the historical audit below. Better Auth email/password accounts, revocable PostgreSQL sessions, owner-scoped PostgreSQL request reads/writes, versioned migrations, canonical assignment checks, and administrator CLI provisioning are implemented. `DemoProvider` is no longer mounted by `app/layout.tsx`; login, shell, dashboard, request form/list/detail do not use browser demo data. Approver/admin workflow routes now show an explicit deferred state. PostgreSQL was not configured in the implementation environment, so live database acceptance remains blocked; see [the current Stage 2 plan](stage-2-plan.md). The original Figma coverage and service tables below remain a record of the pre-Stage-2A baseline.

Audit date: 2026-09-14. ## Remaining work and verification

The only wholly missing Figma frame is the hidden notification flyout. The table above records partial screens and their missing elements; “mapped to a route” does not mean complete. Additional production flows absent from Figma and code include genuine login/recovery/error/session-expiry states, reviewer assignment, account preferences and provisioning-failure/retry states. Those need product decisions and real services, not more demo implementations.

Verified against the final clean production build at `http://127.0.0.1:3100`:

- `npm run lint`, `npm run typecheck`, `npm run build`: passed. The build generated 16 pages. Six existing domain regression tests passed.
- `PLAYWRIGHT_BASE_URL=http://127.0.0.1:3100 npm run test:e2e`: **8 passed** (four new Stage 1 cases plus four existing workflow/layout regressions).
- New requester cases exercised 1440px, 390px and 320px: user-scoped summary counts, Enter/Space disclosure toggles, stable expanded state, readable mobile disclosure position, full information/timeline, approval versus activation, scheduled versus completed expiration, search, combined status/resource filters, inclusive date bounds, invalid date feedback, empty state and clear/reset.
- Renewal navigation was verified to open the existing new-request route with prefill. The complete stored dataset remained byte-identical after filtering, disclosures and opening renewal; no request/grant was mutated by these UI actions.
- Original local images loaded at 1440px, 768px, 390px and 320px. Desktop/tablet retain the image panel; mobile hides it. Changed pages had no document-level horizontal overflow (tables retain local scrolling). No uncaught page errors were recorded by the new scenarios.
- Desktop requester expansion, mobile expansion, desktop/tablet/mobile login screenshots were visually inspected. Existing browser regression also exercised requester, reviewer and administrator routes. Screenshots/traces are in ignored `test-results/`; test source is stored in `tests/e2e/requester-stage1.spec.ts` and `tests/e2e/workflow.spec.ts`.

An initial production run hit a generated-bundle loading error; moving the previous `.next` output aside and rebuilding clean resolved it. The final eight-test run passed against that clean build.
